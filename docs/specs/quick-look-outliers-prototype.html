Quick look: the outliers

The locked quick look spec and its prototype cover the clip row, the reader, the tray and templates. They say nothing about the rest of the clips window: the search bar, the status bar buttons, the update banner, image and HTML and RTF and bookmark clips, clip templates, what happens when a new clip lands while the reader is open, narrow windows, the light theme. This page explores each of those against the same engine, so the pieces can be judged together. Every frame is live: chips pin, the tray appears, quick look opens with Space or the eye, right-click opens the context menu, and / opens search. Tabs and clipboard writes show a toast instead. The theme button at the top switches every frame to the light theme.

1. The bottom stack: tray, search, update, status

Today the bottom of the window is list, search bar (hidden until toggled), update banner (hidden until an update downloads), status bar. The spec adds the tray "under the list, above the status bar" and never says where the search bar goes. Worst case today plus spec is four strips under the list. This frame puts them in one order and shows the two fixes that keep the stack from eating a short window: the tray collapses to one line, and the update banner becomes a pill in the status bar instead of its own strip.

search position update ready

Try it: tick "short window" and watch the tray fold to one line with the exact tab count still on it; "expand" brings the rows back. Switch the update to a status bar pill and the stack loses a strip. Move the search bar to the top to see the alternative: it reads like a find bar and frees the bottom, at the cost of moving the input away from the button that opens it. The status bar keeps three buttons: search, quick look on the newest clip (the rocket's replacement), and settings.

2. Search and filter with chips, pins and the reader

The search bar filters by substring today, drops image clips from the results, keeps each row's real number, and shows "No clips match" when nothing does. None of that changes. What needs deciding is how it meets the new pieces: chips and pins stay live in filtered rows, the reader walks the filtered set and says so, the count line says what was not searched, and one extra toggle ("pinned") shows only clips that contain a pinned value, which is the cross-clip case the tray exists for. Search hits are underlined with a soft mark, not chips, so the two highlights never look alike.

Try it: the filter "INC-4821" is typed already. Press ↓ in the input to move to the first row, Space to open quick look, and walk with ↓: the position reads "2 / 5 filtered" and the row numbers stay 1, 2, 3, 7, 9. Clear the filter (Esc once clears, twice closes the bar). Pin the IP in row 2, then click "pinned" in the search bar to see only the clips that contain a pinned value. Type "sshd" to see the image excluded and the count line say so.

/from a row, open search and focus the input. Ctrl+Shift+F does the same from anywhere, as today. ↓ Enterin the input, move focus to the first visible row. ↓ past the last row returns to the input when the bar is under the list. Escone stack, innermost first: close the context menu, leave edit, close quick look, clear the filter, hide the search bar. Each press does one of those.

3. Image, HTML, RTF and bookmark clips

The spec describes a text reader. Today's list also holds images (a thumbnail with a hover popover that floats over the list), HTML and RTF (shown as raw source with a type label), and bookmarks (title and URL, not clickable). The decision rule says full content is shown only in quick look, inside the window, so the image popover goes and the reader becomes the image viewer. HTML and RTF scan their extracted text, not their markup, so chips land on words and not on tags; the reader offers text, source and (for HTML) rendered views. Bookmarks scan the URL. The rendered view treats the clip as hostile: anyone can put HTML on the clipboard, so the source is parsed inert, cut down to an allowlist of formatting tags with no attributes beyond a safe link target, and shown in a sandboxed frame whose policy forbids scripts, styles, images and network. Row 3 is a clip built to test exactly that. None of these types is editable: edit is greyed in the reader, and Enter on the row opens quick look instead of an editor.

Try it: open row 1 (a screenshot). The reader fits the image to the pane on a checkerboard, the side column lists format, size and pixel dimensions, and edit and wrap are greyed. Walk down to the HTML clip: chips sit on the email in the extracted text; switch the header control to "source" (no chips, no pins) or "rendered". Row 3 is the hostile one: it carries a script, an image with an error handler, a frame, a stylesheet that hides the page, a fixed overlay and a javascript: link. Open it and switch to "rendered": the invoice text shows, the link is dead, the side column lists what was stripped, and nothing runs. The RTF clip has text and source. Row 5 is a bookmark: the URL is a chip, the title is plain. Filtering with text skips the images.

4. A narrow window

There is no minimum window size and users drag the window into a strip beside their browser. The spec sizes the reader from the window, which holds, but its 220px side column and the tray's three-column rows do not fit in 380px. Here the status bar drops its words, the tray stacks each group on its own lines, the reader's matches column folds under the content as a strip that opens on click, and the header drops the size text but keeps every button.

Try it: the tray opens collapsed here, as in short windows; "expand" shows each group stacked with its tools on their own line so the buttons stay full size. Open row 2 and click "Matches" under the content to open the strip. Type in search to see the count line hidden and the input take the width.

5. The list changes under you: new clips, rotation, copies, the context menu

The list is live. A copy in another app inserts a clip at row 1, every row moves down, locked clips keep their slot, and the oldest unlocked clip falls off the end. The spec describes pins and the reader as if the list held still. This frame simulates the traffic: the reader follows its clip by identity and renumbers, pins whose value rotated out are dropped with a notice in the tray, the copied marker (green tick in the number cell, as today) moves with its clip, and Ctrl+Shift+2 shows what a hotkey copy looks like. The context menu is the spec's four items plus the missing home for clip templates, which lose their only screen when the launcher window goes: a "Fill clip template" submenu that previews each template filled from rows 1 and 2. Row 1 cannot be locked or deleted, as today; the items say why.

Try it: pin the IP 198.51.100.7 in row 2 and the ticket. Open quick look on row 2, then press "A copy lands": the reader now says Clip 4, because row 3 is locked and holds its slot, so the clip you were reading jumped over it. Press again and it reads Clip 5. Keep going until the last clip carrying 198.51.100.7 rotates out; the tray drops it and says so. Right-click any row for the menu; hover "Fill clip template" to see the positional templates with their preview. Right-click row 1 to see lock and delete disabled with the reason.

Proposed rules, to fold into the spec

  1. Stack order from the bottom. Status bar, search bar, tray, list. The update banner is a pill in the status bar, never a strip. In a window under 360px tall the tray opens collapsed to one line (summary, exact tab count, expand), which also answers open question 12.3.
  2. Search keeps its contract. Substring, images excluded, real row numbers, "No clips match". Hits get a soft mark, chips stay chips and stay clickable. The count line names what was not searched. A "pinned" toggle filters to clips containing a pinned value. Hiding the bar clears the filter, so there is never an invisible filter.
  3. The reader walks the visible set. Position reads "n / m filtered". If the filter changes and hides the open clip, the reader stays on it, the position says "hidden by filter", and Up and Down jump to the nearest visible clip. The quick look hotkey opens row 1; if a filter hides row 1, the filter is cleared first.
  4. Esc is one stack. Context menu, edit, reader, filter text, search bar. One level per press.
  5. Status bar buttons. Search (on-state while the bar is open), quick look on the newest clip (replaces the rocket, same action as Ctrl+Shift+T), settings. Counts as today.
  6. Types. Images: thumbnail in the row with format, dimensions and size; the reader shows the image fitted; no chips, no edit, no wrap, copy works; the hover popover goes. HTML and RTF: the row shows extracted text with a type tag; scanning runs on the extracted text; the reader has text and source views (HTML also rendered); source view has no chips. Rendered HTML never runs code: the source is parsed with an inert parser, reduced to an allowlist of formatting tags with no attributes except http, https and mailto hrefs and title, and shown in an iframe with an empty sandbox attribute and a CSP of default-src 'none'; images, styles, frames, forms and scripts are stripped and the side column says what was removed; links do nothing inside the frame. The untrusted source is never assigned to the live document. Bookmarks: title plain, URL a chip; the reader shows both lines. Enter on a non-text row opens the reader.
  7. Live list. The reader tracks a clip, not an index. When a new clip lands the reader renumbers in place; when its clip rotates out the reader closes with a toast. Pins whose value no longer appears in any clip are dropped with the tray notice from section 6, with the reason (edited, deleted, rotated out). The copied marker follows its clip.
  8. Copy feedback. Number cell and reader copy set the green tick as today and show a toast. The OS notification fires only for hotkey copies (the window may be hidden), so the user never gets two notices for one copy.
  9. Row 1. Cannot be locked or deleted; the context menu shows both items disabled with "row 1 is the live clipboard". Quick look and pinning work on row 1 like any other row.
  10. Clip templates. A "Fill clip template" submenu in the context menu on every row, listing each positional template with a preview filled from rows 1, 2, 3. Copying toasts like a match template. Which row was right-clicked does not matter, because {c1} is row 1 by definition; whether it should mean "this row" is an open question.
  11. Narrow windows. Under 480px wide: status bar shows counts only, tray groups stack, the reader's matches column folds under the content, the header keeps every button and drops the size text.
  12. Light theme. The clips window keeps its light theme. Group colours have a light-theme set (darker, same hues) so chips pass contrast on both; everything else maps through the same variables. The settings window's light theme stays an open question per 15.8.
  13. Window hide. Hiding the window clears the search bar, as today. Pins, the tray and an open reader survive a hide; they are lost on quit (12.2 leaning no stands).
  14. Delete. Keeps today's behaviour (the row becomes empty in place, nothing shifts) unless a separate decision changes it. The reader and Up/Down skip empty rows, so a deleted row leaves a hole in the list but not in the walk.
