Settings shell, General and Hotkeys: five variations

Variation C is locked in the spec, section 15, as the shell and the General and Hotkeys tabs; the Tools tab is section 14 (prototype). This page makes the other two tabs match it. Every frame below uses the Tools prototype's shell byte for byte: true-black page, Inter plus monospace, 900 x 600 window, 132px left rail with General, Hotkeys and Tools, the same buttons, toggles, footer links, status dots and toasts. Click Tools in any frame and a skeleton of the locked inspector drops in unchanged, which is the test. Five variations, A to E, each with a 900 x 600 frame and a 720 x 440 one. Every control works. Anything that would write to disk shows a toast instead.

Key names follow the platform. Switch it here and every frame re-renders: LinuxWindowsmacOS Stored as CommandOrControl+Shift+V, shown as Ctrl+Shift+V or Cmd+Shift+V.

What the current General and Hotkeys tabs get wrong

Reviewed against src/renderer/src/Settings.tsx and src/renderer/src/components/settings/ on branch t3code/explore-tool-launcher-ux. UX surface only: what each control does, how saving, loading and errors show, how the shell looks. IPC, storage and hook internals were not traced.

Shell and nav

  1. Top tabs with a green underline on a grey page. The active tab is marked with #10b981 (Settings.module.css:57) while every other accent in the app and in the Tools prototype is blue. The page is #1a1a1a with #262626 cards (Settings.module.css:5,84), not the true-black scale the Tools tab now uses.
  2. Content is capped at 64rem and centred (Settings.module.css:26,68), so at the 900px window the cards float inside margins and at 720px the tab strip and the cards shift relative to each other.
  3. General is four stacked cards, each with its own title, and two of them have sub-titles at the same size. Settings.tsx:57-75 mounts User Settings, Updates, Storage, Versions as four section cards. Inside the first, "Application Settings" and "Window Settings" are h3 (ApplicationSettings.tsx:31, WindowSettings.tsx:24), so the hierarchy reads as six equal headings. The Versions card holds one line of text (Versions.tsx:12-16).
  4. Three spinners on first paint. UserSettings, StorageSettings and HotkeyManager each own a loading state (UserSettings.tsx:33, StorageSettings.tsx:17, HotkeyManager.tsx:33), and two different LoadingState components exist (usersettings/LoadingState.tsx, hotkeys/LoadingState.tsx). The error state says "Please try refreshing the application" with no control that does that (ErrorState.tsx:13).
  5. Dead "Close Settings" button. CloseButton renders when onClose is passed (UserSettings.tsx:60, StorageSettings.tsx:33) and Settings.tsx never passes it.
  6. Every component carries its own light-theme branch (classNames(styles.x, { [styles.light]: isLight }), forty-odd sites). Decided in spec 15.2: one variable set, swapped per theme (the theme button at the top of this page shows both), so those branches collapse into the variables rather than being restyled one by one.

General

  1. Saving blocks the whole tab. One saving flag disables every control in both groups (ApplicationSettings.tsx:62,79,93,107,123,138,152; WindowSettings.tsx:37,59,77,91,105) and shows a spinner with "Saving..." under the groups (UserSettings.tsx:57). Toggling Theme greys out Maximum Clips. A failed save goes to console.error only (useUserSettings.ts:92,95); the toggle stays where it was and nothing on screen says why.
  2. Maximum Clips has three waiting states and a 40-word confirm. Typing starts a three second debounce (useUserSettings.ts:144); "Change pending..." appears in bold orange beside the input (ApplicationSettings.tsx:61-65) and again appended to the description (ApplicationSettings.tsx:40). Values over 100 snap back silently; values under 15 correct silently (useUserSettings.ts:114-129). The confirm dialog message computes the loss in one sentence (UserSettings.tsx:63).
  3. Updates live in two places. The Automatic Updates toggle is in Application Settings (ApplicationSettings.tsx:99-113); the Check for Updates button is its own card (Settings.tsx:62, UpdaterControl.tsx) whose helper text sends you back: "configurable in Application Settings" (UpdaterControl.tsx:122-124).
  4. Updater status is a string matched by substring. The dot colour comes from updateStatus.includes('Error') and friends (UpdaterControl.tsx:47-52); Restart & Install appears on includes('downloaded') (UpdaterControl.tsx:107). The status card is always visible, even idle ("Status: Ready"). On macOS the check cannot work (unsigned builds) and nothing says so.
  5. Three numbers in three 80px coloured cards. Total Clips, Locked, Storage Size each get an icon, a colour and a card (StorageStatistics.tsx:21-142, StorageSettings.module.css:117-142). Size is shown as KB to one decimal; the clip count is not related to the maximum it is measured against.
  6. Export, Import and Clear All Data are three equal coloured buttons (DataManagement.tsx:35-80, blue, green, red) with a permanent yellow warning card under them (DataManagement.tsx:82-106). Clear uses confirm() with "cannot be undone" and names nothing it deletes (useStorageSettings.ts:82). Success and failure are alert() (useStorageSettings.ts:54,64,67,90,94,99). Import success says "Please restart the application" with no restart button.
  7. Transparency sub-rows stay visible but disabled when transparency is off (WindowSettings.tsx:43-82), and the slider saves on every input event (WindowSettings.tsx:58), so each 5% notch is a storage write that disables the rest of the tab for its duration.
  8. Auto Start on Linux renders a disabled toggle with the description "Not available on Linux" at full row height (ApplicationSettings.tsx:82-96). Reasonable, but the row earns its place only if it says what to do instead.

Hotkeys

  1. The master switch hides everything. With hotkeys off, the list and the instructions return null (HotkeyList.tsx:32, HotkeyInstructions.tsx:15), so a user who has never turned them on cannot see what they would get.
  2. Raw accelerators on every platform. The key cell shows the stored string, CommandOrControl+Shift+V, in a code element (HotkeyList.tsx:49). macOS users read "CommandOrControl".
  3. Recording does not echo and fails with an alert. Edit flips to Cancel and the cell says "Press keys..." (HotkeyList.tsx:45-47); held modifiers are not shown; a press with no modifier fires alert('Global hotkeys must include at least one modifier key...') (useHotkeyManager.ts:194).
  4. No conflict check, no reset. Two rows can hold the same combination. Defaults exist (src/main/storage/defaults.ts:4-39) and no control reaches them, per row or for all.
  5. ON / OFF text beside every toggle (GlobalToggle.tsx:33-40, HotkeyList.tsx:64-71), which the General tab's toggles do not have. Two toggle implementations (usersettings/ToggleSwitch.tsx, HotkeyManager.module.css .toggle).
  6. Labels and order. "Show/Focus Clipless Window", "Copy 1st Clip" to "Copy 5th Clip", "Open Tools Launcher for Latest Clip", "Search/Filter Clips" (useHotkeyManager.ts:41-50). The launcher entry has to become the quick look hotkey (spec section 9). The five copy rows sit between the window action and the other two.
  7. The numbering rule is explained twice, in the header tooltip (HotkeyHeader.tsx:10-20) and the instructions block (HotkeyInstructions.tsx:30-33). Saving shows "Saving settings..." under the list (hotkeys/SavingIndicator.tsx:13) and disables every row while it runs.

Shared conventions, held by all five

  • Left rail, not top tabs. The Tools prototype frames already use a 132px rail (96px at 720 wide) and the inspector's own header row sits directly under the title bar. Top tabs would add a 34px strip above every tab and push the Tools list pane down, so the Tools frame could not drop in unchanged. The rail also leaves room at the bottom for the version, which is where About's one line of text belongs; a separate Versions card goes away.
  • General applies immediately. Every control is a single independent value with no validation that depends on another control, and today's code already applies per change. What changes is the feedback: a per-control "saved" state for about two seconds, a red "not saved, retry" on failure that puts the control back where it was, and no global spinner and no disabling of other controls. Variation D is the deliberate exception, to test the Save model everywhere.
  • Hotkeys applies immediately too. A shortcut is registered with the OS the moment it is recorded, so the feedback can be truthful: "saved" means it is live. A recording in progress is the one draft, cancelled by Esc, and the old binding stays registered until the new one is accepted. Conflicts with another Clipless shortcut block acceptance and offer a swap.
  • Tools keeps Save. A search term or tool is several fields that are only valid together, and the spec says nothing is stored before Save. Three tabs, two models, one rule: immediate when the control is the whole change, Save when several fields make one change.
  • Toasts only for actions with no visible result. Export, reset all, Save in D, restart and install. A toggle that shows "saved" next to itself gets no toast.
  • Rare actions are footer links. Export data, import data, clear all data, reset all shortcuts. Clear all data is confirmed with the consequence named in numbers.
  • Status dots mean what they mean on Tools. Green is live or healthy, amber needs attention, red is broken or conflicting, grey is off, hollow is informational.
  • Quick look hotkey. "Quick look on newest clip" replaces "Open Tools Launcher for Latest Clip" at Ctrl+Shift+T (Cmd on macOS), per spec section 9.
  • Platform key names. Stored as Electron accelerators; shown as Ctrl / Alt / Shift on Windows and Linux, Cmd / Opt / Shift on macOS. Start with the system is hidden on Linux rather than shown disabled. Updates on macOS show a link to releases instead of a check button (the builds are unsigned; see the gotcha in the brain).

In every frame: turn on "Start with the system" to see the error state (the prototype fails that one on purpose, as a real registration failure would look). Set "Clips to keep" below 87 to see the confirm that names the loss. Click any shortcut's recorder and press Ctrl+Shift+2 to see a conflict and the swap offer. Click "clear all data" in a footer.

A Stack

The closest to today's structure, restyled. General is one scrolling column with five section headings (Application, Window, Storage, Updates, About) and a row per control: label and one-line description on the left, status and control on the right. Storage is one line of numbers with a usage bar; the three data actions are footer links. Hotkeys is the master toggle, then one row per shortcut with keycaps, a Record button and an enable toggle. Each control shows "saved" inline for two seconds after it applies.

Record changes the keycaps into a live recorder that echoes held modifiers. With hotkeys off, the list is hidden, as today, to show what that costs next to B through E, which dim it instead.

Behaviour

  • Each control has its own status slot: "saving" (dim), "saved" (green, two seconds), "not saved, retry" (red, stays until retried). Other controls never lock.
  • Clips to keep applies on Enter or blur; out of range shows "15 to 100" in red and does not apply. Below the current count it asks, naming the number deleted and that locked clips stay.
  • Transparency off hides its two sub-rows.
  • Updates row: dot and one line of status, Check now button; on macOS a releases link instead.
  • Hotkeys: Record button, Esc cancels, modifier-less press shows "needs Ctrl, Shift or Alt" inline, conflict shows the other shortcut's name and a swap link. "reset" appears on a row when it differs from the default; "reset all" is a footer link.

Trade-offs

  • General scrolls at 900 x 600 (about one screen and a third) and scrolls more at 720 x 440. Section headings keep it navigable but there is no way to jump.
  • Hiding the list when hotkeys are off repeats today's mistake; it is here for comparison only.
  • The Record button is one more control per row; the keycap itself could be the button (see C and E).
  • Visually closest to the Tools inspector's Edit view, but General has no list pane, so the two tabs share widgets rather than layout.

B Two panes everywhere

The Tools layout applied to both tabs. General has a list pane of its five groups, each with a status dot, and an inspector showing the selected group's rows. Hotkeys has a list pane of shortcuts with dots (green live, grey off, red conflict) and keycaps, and an inspector for the selected one: large keycaps, Record, Reset to default, what it does, and the conflict text if any. Data actions sit in the list pane footer, like export and import on Tools.

Walk the Hotkeys list with a click; the inspector follows. Select Storage to see the stats with the clear-all link under them. The master toggle is the first row of the Hotkeys list pane.

Behaviour

  • Same immediate apply and inline status as A.
  • General dots: Storage turns amber at 90% of the clip limit; Updates takes the updater's state (grey idle, blue checking, green downloaded, red error); About is hollow.
  • Hotkeys dots: green when enabled and bound, grey when off, red when the key is also held by another row. Conflicts are visible from the list without opening anything.
  • Hotkeys off dims the list pane and inspector; rows stay readable.

Trade-offs

  • Strongest resemblance to Tools: three tabs, one layout. A user who learns one learns all.
  • General has five fixed groups, so a 250px list pane for five rows is mostly empty. Window and About are two clicks from Application where A shows them in one scroll.
  • At 720 x 440 the list pane narrows to 196px and the inspector has about 420px for controls; fine for rows, tight for the stats line.
  • Eight shortcuts do not need an inspector; the detail view is mostly the same row, bigger.

C Dense grid, no scroll

General fits in one 900 x 600 screen: Application and Window side by side, then Storage, Updates and About as three short panels across the bottom. Rows drop their description; the label carries it as a tooltip. The three bottom panels stack their content instead of running it in a line: Storage is the clip count large, a full-width usage bar, then locked count and size on one line; Updates is the check-on-start toggle, a status line with its dot and one line of detail, then the button; About is the version, the runtime, then the links. Hotkeys is a table (action, shortcut, on, reset) where the keycap itself is the recorder. At 720 x 440 the grid collapses to one column and scrolls.

Click any keycap in the Hotkeys table to record into it. Hover a label in General for the description.

Behaviour

  • Everything on General is visible at once at 900 x 600; nothing scrolls.
  • Hotkeys table: click the keycap, press the combination, done. Esc cancels. Conflict and modifier messages appear in the row under the keycap.
  • Same immediate apply and inline status.

Trade-offs

  • Descriptions behind tooltips are descriptions nobody reads. "Opaque when focused" and "Remember window position" survive it; "Code detection" does not.
  • The grid only holds at 900 x 600 with the exact row count we have today. Two more settings and it scrolls anyway, at which point it is A with panels.
  • Panels inside the page repeat the card-inside-card look of today's settings, which the Tools prototype moved away from.
  • The table for Hotkeys is the most legible of the five for scanning eight rows, and the keycap-as-recorder is the best recording interaction.

D Draft and Save

The Tools model applied to everything: nothing is stored until Save. Same stack as A, but a change marks its row with a blue edge and counts in a save bar at the bottom ("3 unsaved changes, Discard, Save"). Recording a shortcut fills the row but registers nothing until Save. Switching tabs with unsaved changes asks. Storage actions (export, import, clear) are operations, not settings, and still act at once.

Flip three toggles, then click Hotkeys in the rail: the prompt offers Save, Discard or stay. Save shows a toast with the count.

Behaviour

  • Rows show a dirty edge; the save bar shows the count and turns blue when non-zero.
  • Save applies everything and toasts the count. Discard reverts every row. Both are disabled at zero.
  • Clips to keep still confirms the loss, but at Save time, once, for the final value.
  • Hotkeys: recording works as in A; the new binding shows in the row, with the old one still live until Save.

Trade-offs

  • One model across all three tabs, and the user never wonders whether a change took.
  • A toggle that does nothing when flipped is wrong. Theme and Always on top are the worst cases: the user flips them to see the effect, and sees nothing.
  • The leave-tab prompt is a dialog every session for anyone who adjusts one thing and clicks away.
  • Hotkeys with a pending binding and a live old one is two states per row to explain.

E Stack with a jump bar, undo, and the keycap as recorder

A, with what B and C got right folded in. General keeps the single column, but a jump bar under the title bar names the five sections and scrolls to them, so nothing is hidden and nothing is two clicks away. "saved" carries an undo link for five seconds. Export, import and clear all live in a collapsed Data row at the end of Storage that states the consequence before showing the links. Hotkeys is the list with the keycap as the recorder, conflicts against Clipless and against combinations the OS keeps for itself, a per-row reset on hover, and the master toggle dimming rather than hiding the list.

Change Theme, then click "undo" in the saved state. Record Ctrl+Shift+Esc on Windows key names, or Cmd+Shift+4 on macOS, to see the amber OS warning (it does not block). Open the Data row.

Behaviour

  • Jump bar: click scrolls to the section and highlights the entry; scrolling updates the highlight.
  • Inline status "saved, undo" for five seconds; undo re-applies the previous value through the same path and shows "saved" again without undo.
  • Data row collapsed by default; opened, it reads "87 clips, 4 locked, 212 KB. Export makes a JSON backup. Import replaces everything and restarts. Clear all deletes everything." with the three links under it.
  • Hotkeys: keycap click records in place; Esc cancels; no modifier shows red inline; Clipless conflict shows the other row's name with "swap"; OS-reserved combination shows an amber line and is accepted.
  • Master toggle off dims the list at 45% and blocks recording; rows remain readable.

Trade-offs

  • The jump bar is a second row of tabs, which is exactly what the rail was chosen to avoid. It is inside the pane and reads as a table of contents, but it is still horizontal navigation.
  • Undo on a toggle is one more thing in the row for two seconds; cheap, and it makes "applies immediately" safe to trust.
  • No list pane, so General and Hotkeys share the shell, the widgets and the footer with Tools, not its two-pane layout.
  • The OS-reserved list has to be maintained by hand and will never be complete.

Recommendation

Chosen on review: C, the dense grid, after a polish pass on the three bottom panels (they stack their content now instead of wrapping a one-line layout word by word). The first recommendation on this page was E; on review the no-scroll General won, because every setting is visible at once and the Hotkeys table scans best of the five. Keep the rail. Keep immediate apply on General and Hotkeys and Save on Tools, for the reason under shared conventions.

Grafts worth carrying into C from the others: B's red dot in the Hotkeys list for a conflicting shortcut, so a conflict is visible before you touch the row; E's undo link on the inline "saved" state; E's amber line for combinations the OS keeps for itself; and E's consequence text (counts and size) next to the data links, either in the footer or in the clear-all confirm, which C already has.

What C costs, to keep in mind. Descriptions live behind tooltips, so a label has to carry its meaning alone; "Opaque when focused" does, "Code detection" is borderline and may want a longer label. The no-scroll fit depends on today's control count: two more rows in Application and the grid scrolls at 900 x 600, which is still fine, it just stops being the selling point.

Why not B, the most Tools-like. A two-pane layout earns its list pane when the list is user-made and open-ended, which search terms, tools and templates are. General's five groups and eight shortcuts are fixed, so the list pane is five or eight rows of navigation for content that fits on one screen. Why not D. A theme toggle that does not change the theme until Save is a broken toggle. Why not E. It answers "where am I" with a second row of navigation inside the pane; C answers it by showing everything.

Open points to settle in the spec: whether the jump bar highlights on scroll or only on click (the prototype does both); and the OS-reserved list, which should start small (task manager, Alt+F4, Spotlight, macOS screenshots, Cmd+Q, Cmd+Tab, Alt+Tab) and be marked as advisory.

Implementation notes

  • One shell. Settings.tsx renders the rail, the title bar content and one main; each tab is a component that fills it. The tab strip, the 64rem cap and the section cards go. The version moves to the bottom of the rail and Versions.tsx goes with the card.
  • One per-control status. useUserSettings replaces its single saving boolean with a map of key to saving | saved | error, cleared by a timer. No control is ever disabled by another control's save. The two SavingIndicators, the two LoadingStates and ErrorState collapse into one small status component used by both tabs.
  • One toggle. ToggleSwitch without the ON/OFF text, used by Hotkeys too. HotkeyManager.module.css's own toggle goes.
  • Clips to keep applies on commit (Enter or blur), not on a debounce, validates in place, and asks once when the new limit is below the current count, with the numbers in the message.
  • Updates is one group: the check-on-start toggle and the status row together. The updater exposes a state enum (idle, checking, available, downloading, downloaded, upToDate, error with message) instead of a display string; the dot colour maps from the enum. On macOS the row shows a releases link and no button.
  • Storage exposes the count, the locked count and the size in bytes; the row formats them and draws the usage bar against maxClips. Clear all confirms with those numbers. alert() and confirm() go; results are toasts, failures are inline text.
  • Hotkeys display function: accelerator string to platform key names, one place. Recording echoes held modifiers from keydown, accepts on the first non-modifier key, and validates inline. Conflict check is a lookup over the other seven rows before accepting; swap writes both rows. Defaults come from the same DEFAULT_HOTKEY_SETTINGS the main process uses, exposed to the renderer. The openToolsLauncher entry is renamed to the quick look action when section 9 lands.
  • Master off keeps rendering the list at reduced opacity with recording disabled.
