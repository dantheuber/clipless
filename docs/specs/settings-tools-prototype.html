Settings, Tools tab: the master-detail inspector, locked

The chosen design for Settings > Tools, where search terms, tools and templates are made. It was chosen on review from five variations (tabs plus a groups rail, groups first, a flow board, a sample-first workbench, and this inspector), then polished: a list pane of everything on the left, an inspector on the right with Edit and Uses, a health overview when nothing is selected, a "start from" page for new search terms, and a per-group colour bucket. It speaks the vocabulary of the redesign spec (section 14 covers this tab): a search term produces capture groups, a tool or template consumes them, and a thing is ready only when every token it needs has a producer. Two frames below: the default 900 x 600 settings window, and a 720 x 440 one to show the same layout holding together when the window is dragged small. Everything runs against the sample text; Save, Add, Export and Import show toasts instead of writing anything.

What is locked in

  • Two panes, no sub-tabs. The list pane holds search terms, tools and templates in collapsible sections with counts and a + each. Every row carries a health dot (green ready, amber producer disabled, red orphan, grey off, hollow for clip templates) and a strip of swatches for the groups it produces or needs. The inspector shows the selected item or, with nothing selected, the overview. The Test Patterns tab is gone; every editor previews live.
  • Edit and Uses. Edit is the editor with the sample text pinned above it: chips for a search term, resolved URLs and an exact tab count for a tool, generated text for a template. Uses is the relationship view for that one item, in both directions, with the fix next to any token nobody produces: enable the disabled producer, add the library pattern for that group, or write a new term with the group prefilled.
  • Colour belongs to the group. Click any group pill in the inspector and a bucket of twelve swatches opens. The six prototype colours are defaults for ip, email, ticket, domain, url, user; any new group takes the next free colour; a swatch another group uses carries a dot and names it on hover; reset restores the default. Tools and templates never get a colour of their own.
  • Tokens are picked, orphans are flagged. The picker lists groups that have a producer. A token typed by hand that nothing produces gets a wavy red underline in the preview and a red "never ready" readiness line. The two kinds of not-ready stay distinct: "never ready" is a config problem, "sample lacks ticket" is a property of this text.
  • The library is a starting point. New search term opens "start from": every built-in with its regex, a description, an "already added" state, and "finds N in the sample" when it would catch something. Adding copies it in as a normal term with an enabled toggle. Adding one that exists but is disabled re-enables it. Nothing from the library runs on its own.
  • Nothing is stored until Save. Cancel leaves no record. Save is disabled while the pattern is invalid, has no named group, uses a reserved c1 style name, or the name is empty.
  • Export and import are footer links. Export shows the counts and the JSON, including groupColours. Import shows what it would add, and which groups, before offering merge or replace. Failure is inline text.

Default window, 900 x 600

Try it: click ticket in the overview and pick a swatch; the list strips, the pills and the preview chips follow. Hover the red swatch: "also used by ip". Select Directory, open Uses: user has no producer and the fix buttons are right there; "new term for user" opens the editor with (?<user>) prefilled. Select VirusTotal: the preview lists both IPs from the sample as two tabs; add a third IP to the sample and it becomes three. Press + next to Search terms, pick "GUID": the editor opens with the pattern filled and guid already wearing the next free colour. The back arrow in the header returns to the overview.

Compact window, 720 x 440

Same code, smaller frame. The list pane narrows to 196px, the header drops its hint text, the sample box shrinks to one line. Open Incident Summary's Uses and the three tokens still fit without scrolling; the list pane and an open editor scroll inside their own panes when they have to, and the header, footer and nav never move.

The list dot and the overview reflect config readiness only. "Sample lacks X" never changes a dot, because the dot has to mean the same thing whatever text happens to be in the sample box.

Colours

  • The bucket: Twelve, fixed, chosen to pass contrast on both themes. No hex input.
  • Defaults: the prototype's six for the six named groups. Any other group takes the next free colour at the moment it first appears in a pattern, so the first twelve groups are distinct with no action from the user.
  • Sharing a colour is allowed and never silent: the swatch shows a dot and the tooltip names the other group.
  • Stored as a groupColours map keyed by group name, alongside search terms in the Quick Clips config, and exported with it. An entry whose group no longer appears in any pattern, URL or template is dropped. Keying on the search term would be wrong: one group can come from two terms, one term can produce two groups.
  • The template pill's yellow and the tool pill's grey are type colours, the same for every template and every tool, and stay out of the bucket.

Keyboard (spec, not in this prototype)

↑↓move the selection in the list pane; the inspector follows on Uses, not Edit, so walking the list never discards an edit. Enteropen Edit for the selected item. Spaceon a search term row, toggle enabled. Esccancel an edit and return to Uses; a second Esc returns to the overview. Ctrl+S(Cmd+S on macOS) save the open editor when Save is enabled. Deleteask to delete the selected item, naming what depends on it. Tabcycles the open editor's controls and stays inside it.

Planned additions, not in this prototype

  • Tray preview in the overview. Under the sample text, the launch tray that pinning everything in the sample would produce, drawn with the tray's own rules (every token pinned, multiplier per value, exact tab count). The one place settings and the clips window can be checked against each other by eye. Taken from variation D.
  • Problems filter on the list pane. One toggle that hides everything green.
  • Library suggestions from the sample. At the top of "start from": "Phone number would find 1 value in your sample".
  • Delete confirmation that names dependents. Deleting a term whose group feeds two tools says so.

What the current settings get wrong, and what this design does about it

Reviewed against src/renderer/src/components/settings/ on branch t3code/explore-tool-launcher-ux. Line numbers are from that tree.

  1. Two managers, three copies of the pattern library. Settings.tsx:10,84 mounts ToolsManager. QuickClipsManager.tsx is a dead near-duplicate of it (same state, same handlers, no templates tab). Each file declares its own BUILTIN_PATTERNS, and none of them is the one the UI uses: SearchTermsSection.tsx:10-51 has a third copy with the TLD-aware domain regex and a GUID entry that the other two lack. QuickClipsManager.tsx:11, ToolsManager.tsx:305, SearchTermsSection.tsx:10
  2. Capture groups have no colour and no identity. Groups render as identical accent-blue pills (.captureGroup, QuickClipsManager.module.css:849) and template tokens as grey ones (.token, TemplateManager.module.css:420). Nothing connects the word ip in settings to the red chip the user will click in the clip list. SearchTermsSection.tsx:240-247, ToolsSection.tsx:126-131, TemplateManager.tsx:1055-1064
  3. Tokens are typed from memory, and nothing checks them. The tool editor is a bare URL input with placeholder text (ToolsSection.tsx:114-120); it lists "Detected capture groups" parsed out of the URL but never compares them with the groups any search term produces. The default new tool is {email|domainName} (ToolsManager.tsx:484) while the library produces ipAddress, domainName, phoneNumber, so the sample vocabulary disagrees with the prototype's ip, domain. An orphan token (no producer) looks exactly like a good one. ToolsSection.tsx:40-53, ToolsManager.tsx:500-516
  4. No relationship view in any direction. A search term card shows the groups it produces (SearchTermsSection.tsx:272-283) but not who consumes them. A tool card shows "Supported Groups" (ToolsSection.tsx:194-203) but not which search terms feed it. TemplateManager is a separate component with its own loading and no access to search terms or tools at all (TemplateManager.tsx:787-818), so it cannot say whether a template's tokens are producible.
  5. Readiness is not a concept here, and the help text teaches the old rule. The tools tooltip says "If any of these groups are found, each match will open in its own tab" (ToolsSection.tsx:78-84), which is the compatibility rule section 8 of the spec removes. There is no place that says "this tool needs ip and ticket" or "this template will never be ready because nothing produces user".
  6. Preview is a separate tab, a button press and a round trip away. "Test Patterns" is its own sub-tab; you paste text, press a button, and get name: value rows back from window.api.quickClipsScanText (TestPatternsSection.tsx:241-247, 264-287). You cannot see chips, you cannot test the pattern you are editing without saving it first, and there is no preview at all for a tool URL or a template's output. Pattern validation runs against a fixed lorem sentence (SAMPLE_TEXT, SearchTermsSection.tsx:70) rather than the user's text.
  7. The built-in library is a <select> that fires on change. SearchTermsSection.tsx:144-160. You cannot read the regex before adding, there is no "already added" state, adding IP twice makes two identical terms, and once added the only way to turn a pattern off is to delete it. SearchTerm.enabled exists (shared/types.ts:168) and the scanner honours it (quick-clips.ts:12), but no control in settings sets it.
  8. Create writes a placeholder record before you have typed anything. "New Search Term" with (?<value>my_pattern), "New Tool" with an example URL, "New Template" with four positional tokens (ToolsManager.tsx:417, 482-486; TemplateManager.tsx:782, 822). Cancel keeps the junk. Only one item per tab can be in edit at a time, and switching sub-tabs drops the expanded state.
  9. Export and import are the two most prominent buttons on the page. They sit in the header above the sub-tabs (ToolsManager.tsx:645-666), import replaces silently with no summary of what came in, and failure is a browser alert() (ToolsManager.tsx:638). Team sharing matters, but it is a once-a-quarter action sitting where the every-day actions should be.
  10. Clip templates and match templates are mixed in one list. {c1} templates are not match-driven and never appear in the tray (spec section 7), but the manager shows them identically and the tooltip (TemplateManager.tsx:996-1005) still says matching templates "appear in the Tools Launcher".

Answered above

  • One manager, one library: the list pane loads search terms, tools and templates together; one BUILTIN_PATTERNS in the new vocabulary.
  • Groups carry one colour everywhere, chosen from the bucket.
  • Tokens are picked from groups with a producer; typed orphans are flagged before Save.
  • Uses and the overview answer the relationship question in both directions, with the fix beside the problem.
  • Readiness has four wordings and the help text teaches the every-token-pinned rule.
  • Every editor previews against the sample text before Save; no Test Patterns tab.
  • The library is a start-from page with the regex visible, added state, and re-enable instead of duplicate; every term has an enabled toggle.
  • Nothing is stored before Save; Cancel leaves nothing behind.
  • Export and import are footer links; import previews before it changes anything.
  • Clip templates are labelled as such and stay out of Uses.

Implementation notes

  • One data source for the tab. Search terms, tools and templates load together; the inspector's Uses and the overview are derived from that one set. Today's TemplateManager loads on its own and cannot see search terms; it folds into the same component tree.
  • One BUILTIN_PATTERNS. The three copies (QuickClipsManager, ToolsManager, SearchTermsSection) become one, with group names in the new vocabulary (ip, domain, phone, mac, guid) and the TLD-aware domain regex. QuickClipsManager.tsx is dead and goes.
  • Scanning in the renderer for previews. The editors run the pattern under edit against the sample text locally with the d flag for group positions; this is the same scan the clip list uses for chips, and it must be, so the two cannot disagree. quickClipsScanText over IPC is no longer needed for settings.
  • Readiness is one function. needs(groups) x producers(enabled) x sample values gives the four wordings above; the tray in the clips window uses the same function with pins instead of sample values.
  • Colours. groupColours lives next to search terms in storage and in the export format. A resolver takes a group name and returns the override, the named default, or the next free palette entry, and the clip list, the tray and settings all call it.
  • Inspector state. selected item (kind, id) or none; tab (edit or uses); a draft for "start from". Switching selection while an edit is dirty asks once.
